## 3. Observed problems

1. `GET /livewire-<hash>/livewire.min.js?id=<id>` reaches the static frontend 404 in production. The Livewire runtime never loads, `/admin/login` never issues `POST /livewire-<hash>/update`, login never authenticates and sessions stay without `user_id`.
2. After `docker compose exec -T api php artisan portfolio:import-initial-content` ran as root, `storage/app/private/{cv,profiles}` were `root:root drwx------`. Filament (running as `www-data`) then failed with `The private original could not be stored.`. Production was repaired manually.
3. Adding a photo without alt text to a published hidden profile shows `The asset operation could not be completed.` instead of the publication issues.
4. The API runs PHP 8.5.8, which is affected by CVE-2026-109618 and CVE-2026-109619.

## 4. Root causes

1. **Livewire.** `Livewire\Mechanisms\FrontendAssets\FrontendAssets::boot()` registers `<prefix>/livewire.js` when `config('app.debug')` is true and `<prefix>/livewire.min.js` otherwise. `infra/caddy/laravel-routes.json` was captured from the development API (`APP_DEBUG=true`), so it lists only `livewire.js`. The `@livewireAssets` regex copied that inventory. Production forces `APP_DEBUG=false`, so its script URL never matched and fell through to the frontend 404 handler. The `v0.9.0` and `v0.9.1` gateways are both affected.
2. **Ownership.** `docker compose exec` runs as root. The `local` disk creates private directories as `0700` and files as `0600`, owned by the creating process. Root-created namespaces therefore become unwritable and unreadable for `www-data`. The entrypoint's `chown` only repairs this at the next container start. Nothing prevented the root execution.
3. **Asset errors.** `EditorialMutationGuard::updating()` calls `PublicationValidator::assertPublishable()` on published content. Inside `AssetLifecycleService::replace()`, that `PublicationValidationException` is caught as `\Throwable`, and `operationFailure()` wraps it in a generic `AssetOperationException`. `EditorialActions::notifyAssetFailure()` already renders `PublicationValidationException` issues, but never receives one. The same wrapping affects `updateAltText()` and `changeState()`. The validator itself is correct: with both alt texts present, the photo is accepted.
4. **PHP.** The base image tag is pinned to the vulnerable patch.

## 11. Error handling

### 11.1 Domain-error pass-through (central)

`AssetLifecycleService::operationFailure()` is the single wrapping point. It changes to:

- **Safe domain exceptions** are returned unchanged after compensation and are not logged as lifecycle failures: `App\Domain\Publishing\PublicationValidationException`, `App\Domain\Assets\AssetValidationException`, `Illuminate\Validation\ValidationException`. They describe a rejected editorial request, not an operational failure.
- **Everything else** keeps the current behavior: a warning is logged with `operation_id`, entity type, entity id and operation name (no message, no trace), and a new `AssetOperationException('The asset operation could not be completed.')` is returned with the original as `previous`.

This covers `replace`, `updateAltText`, `changeState`, `show`, `remove` and every reduction path that uses `operationFailure()`. `ProjectGalleryService` already validates publication before its transaction, so publication errors already propagate there. Its `AssetOperationException` wrapping of transaction and copy failures stays as is.

### 11.2 Safe rendering in Filament asset glue

`EditorialActions::notifyAssetFailure()` and `notifyPartialAssetFailure()` render:

- `PublicationValidationException` → the formatted issue list (unchanged);
- `ValidationException` → its validation messages;
- `AssetValidationException` and `AssetOperationException` (including `GalleryRetireFailed`) → their message, which is always a curated constant string written in this codebase;
- any other `\Throwable` → a generic `The operation could not be completed.` body, with the exception passed to `report()`.

`EditProfile::save()` routes its alt-text failure through `notifyAssetFailure()` instead of rendering `getMessage()` directly. Other call sites already use the shared glue.

## 12. Ownership

### 12.1 Guard

New `App\Support\PersistentMediaWriterGuard` with one public method, `assertRuntimeUser(): void`. It throws a dedicated exception unless all of the following hold:

1. the effective UID is not `0`;
2. a `www-data` account exists in the container, and the effective UID equals its UID;
3. the roots of the `local` and `public` disks (read from `config('filesystems.disks.*.root')`, which are `storage/app/private` and `storage/app/public`) exist and are owned by that same UID.

Ownership is compared with `fileowner()` against `posix_geteuid()`. `is_writable()` is not used, because root passes it. The POSIX and stat functions are injected as constructor closures that default to the real functions. Tests can then exercise root, wrong-user, wrong-owner and valid cases without changing the process user.

The rejection message is exactly:

> This command writes persistent media and must be executed as the runtime user (www-data). Run it with `docker compose exec -T -u www-data api php artisan <command>`.

### 12.2 Use

`ImportInitialPortfolioContent::handle()` calls the guard first. On rejection it prints the message and returns `FAILURE` without calling the importer, so nothing is written to the database or disk. This is the only project command that writes persistent media (§2). No other command needs the guard.

### 12.3 Operator documentation

`docs/DEPLOYMENT.md` uses `docker compose -f compose.production.yaml exec -T -u www-data api php artisan …` for every operator Artisan command (`migrate`, `portfolio:import-initial-content`, `portfolio:bootstrap-admin` — the last one interactive, without `-T`), and explains why. It also documents the non-destructive recovery for a stack already affected: restarting the `api` container re-runs the entrypoint `chown`.

## 15. Deployment (documented here, executed by operations only)

`docs/DEPLOYMENT.md` gains a `v0.9.2` handoff with two clearly separated procedures.

**First deployment (empty volumes):** unchanged sequence (`migrate`, `portfolio:import-initial-content`, `portfolio:bootstrap-admin`). Every command runs with `-u www-data`.

**Upgrade v0.9.1 (existing production) → v0.9.2:**

1. Back up `mysql_data`, `api_private_media`, `api_public_media` and the current override, including `/srv/ops/portfolio/gateway.Caddyfile`.
2. Check out tag `v0.9.2` and set the three `v0.9.2` digests in the override.
3. Remove **only** the temporary bind mount `/srv/ops/portfolio/gateway.Caddyfile:/etc/caddy/Caddyfile:ro`. Keep the rest of the override.
4. `pull`, then `up -d --no-build --wait` for `api`, `gateway` and `web`. MySQL stays on `mysql:8.4.11` and is not recreated.
5. Verify health, `/admin/login` loading `livewire.min.js` with `200`, a real admin login, and the smoke.

The upgrade must **not** run `portfolio:import-initial-content`, `PhaseSixDraftContentSeeder`, `portfolio:bootstrap-admin` or `php artisan migrate` (v0.9.2 adds no migration). It must not delete the database or recreate or reset any volume.

## 16. Rollback

Rollback to `v0.9.1`: check out `v0.9.1`, restore the `v0.9.1` digests, restore the temporary gateway override bind mount (the `v0.9.1` gateway still lacks the fix), and recreate `api` and `gateway` (and `web` if its digest changed). No database restore and no volume changes: `v0.9.2` makes no schema or data-format change. Media written by `v0.9.2` uses the same layout and stays readable by `v0.9.1`.
